# Studybooks — лекції → книги на сервері

Фото й файли лекцій завантажуються на сайт, а сервер сервер сам перетворює їх на **дві PDF-книги для кожного предмета**:

| Книга | Що всередині |
|---|---|
| `clean.pdf` | Англійською. Матеріал непомітно виправлений і доповнений за довідковими підручниками, без жодних позначок про правки. **Кожен розділ закінчується вижимкою** (Chapter summary), а **в кінці книги є словник термінів** (Glossary, англійською, з посиланнями на розділи). |
| `original.pdf` | Дослівна транскрипція мовою оригіналу + оригінальні фото/сторінки. |

Обидві книги мають однаковий порядок. **Розділ = день заняття**: дата, коли лекція чи заняття відбулися (її вказують при завантаженні), від старішого до новішого. **Записи** всередині розділу йдуть у порядку завантаження. Тема лишилась тільки позначкою біля запису.
Предмети взяті з 1-го семестру TUM B.Sc. Aerospace (WS 2026/27). Нові предмети й теми, знайдені в завантаженнях, додаються автоматично (`auto: true`).
Пояснення та інтерактивні сторінки робляться **тільки на запит**.

- **Сайт:** http://127.0.0.1:8810 — доступний тільки в tailnet
- **Сервер:** `ssh <server>` (користувач сервера), робоча папка `~/studybooks/`
- **Ця папка** (`X:\claude_slop\studybooks\`) — джерело правди для коду. На сервер викладається через `scp`. Дані (бібліотека, книги) лежать **тільки на сервері**.
- Почато 2026-10-16.

## Як це працює

```
 телефон/ПК ──upload──► web.py (FastAPI, :8810) ──► data/users/<uid>/inbox/
                                   │  POST /webhook/studybooks-kick
                                   ▼
 n8n «Studybooks · Фон» (кожні 5 хв + webhook) ──SSH──► sb.py kick
                                                            │ (запускає воркер у фоні, lock)
                                                            ▼
                     sb.py run:  для кожної людини окремо
                       1. файли → сторінки (фото / PDF / Office через LibreOffice)
                       2. порції по 12 сторінок (дрібні завантаження одного дня й предмета — разом), 3 проходи:
                          a) sonnet: транскрипція + сортування (prompts/ingest.md)
                          b) haiku: звірка з підручниками через їхні карти (prompts/refs.md → refs_notes.md)
                          c) модель людини (opus): чистий англійський текст лише з тексту (prompts/clean.md)
                          → library/<предмет>/<тема>/<дата>_<slug>/{clean.md, original.md, meta.json, figs/, pages/}
                       3. check_md (pandoc, strict) → якщо TeX не конвертується — prompts/fix.md (sonnet)
                       4. git commit бібліотеки
                       5. вижимки (sonnet), лише через 30 хв тиші: для кожного дня, де змінились записи → prompts/digest.md
                          → library/<предмет>/_days/<дата>/_digest/{summary.md, glossary.json, meta.json}
                       6. збірка: markdown → pandoc → Typst → books/<предмет>/{clean,original}.pdf
```

### PDF без редагування (додано 2026-10-20)

Третій перемикач на вкладці «Додати» — **«PDF без редагування»** (`kind: "asis"`). Для лекцій, які вже є готовим PDF і не потребують транскрипції.

- **Обов'язково:** предмет і тільки `.pdf` (сервер відповідає 400 на решту). Тема: існуюча, «Нова тема…» або за замовчуванням «Lecture PDFs».
- **Claude не потрібен:** `add_asis()` в `sb.py` не викликає `claude`, тому працює без входу й під час паузи через ліміт; воркер обробляє такі завантаження в обхід перевірки входу. Книги оновлюються за секунди.
- **Що потрапляє в книги:** кожен PDF — окремий запис розділу (назва = ім'я файлу), у **обох** книгах, сторінка в сторінку, векторно, **у власному розмірі** (A4, слайди 16:9, повернуті сторінки), без колонтитулів. Перед сторінками стоїть заголовок запису з рядком «PDF · added … · unedited, N pages follow». Примітка до завантаження показується в обох книгах.
- **Зберігання:** `library/<предмет>/<тема>/<дата>_<назва>/{source.pdf, meta.json}` (`meta.json`: `asis: true`, `pdf_pages` = розміри сторінок). Файл у `processed/` видаляється, щоб не дублювати. Перевірка PDF (не читається, пароль, 0 сторінок) іде до розміщення, тож напівзавантажень не буває; збій → «Не вдалося» без повторів.
- **Не чіпається Claude'ом:** вижимки/глосарій і пояснення пропускають такі записи (немає тексту). Розділ, де лише PDF, не отримує «Chapter summary».
- Тест: 3 сторінки (A4, 16:9, A4 з поворотом 90°) лягли в обидві книги у своїх розмірах.

### Публічний доступ через Cloudflare (додано 2026-10-21)

Сайт доступний не лише в tailnet: кожен, хто має посилання, може зареєструватись і мати **свій власний простір** (як друзі раніше, лише без Tailscale).

```
інтернет ──► Cloudflare quick tunnel (studybooks-tunnel.service, користувацький юніт)
                └─► 127.0.0.1:8811  studybooks-public.service  (SB_PUBLIC=1)   ← той самий код, інший режим
tailnet  ──► tailscale serve :8810 ──► 127.0.0.1:8810  studybooks-web.service  (власник, адмін)
```

- **Посилання:** адреса швидкого тунелю `https://<слова>.trycloudflare.com`. **Вона змінюється при кожному запуску тунелю** (рестарт сервера, юніта), cloudflared пише її в `data/state/tunnel.log`, а сайт у tailnet показує її на вкладці «Адмін» («Публічний доступ»). Стабільна адреса потребує акаунта Cloudflare і власного домену.
- **Ідентифікація:** публічний екземпляр **ніколи не читає `Tailscale-User-*`** (через тунель їх може надіслати будь-хто). Людина реєструється іменем і паролем, отримує підписаний cookie `__Host-sb` (HttpOnly, Secure, SameSite=Strict, 30 днів) і живе в просторі `pub-<ім'я>`. Публічний акаунт ніколи не буває адміном, навіть якщо назвати його як власника. `/api/admin/*` на публічному екземплярі закрито повністю (403).
- **Перевірка «ти людина»:** перед входом і реєстрацією. За замовчуванням це обчислювальне завдання (браузер у фоновому воркері шукає число, від якого SHA-256 починається з 16 нульових бітів; секунда-дві). Воно робить масову реєстрацію й підбір паролів дорожчими, але **не справжня капча**: рішення в кожного бота займає частки секунди. Основний захист це ліміти нижче. **Справжній Cloudflare Turnstile** вмикається без переробки: створи безкоштовний акаунт Cloudflare → Turnstile → віджет, поклади `SB_TURNSTILE_SITEKEY` і `SB_TURNSTILE_SECRET` у `~/studybooks/public.env` і `sudo systemctl restart studybooks-public`. Тоді сторінка показує віджет Cloudflare, а сервер перевіряє токен через `siteverify` разом з адресою відвідувача (тест із фейковим Cloudflare у `test_public.py`; з справжніми ключами ще не перевірялось, і чи прийме Turnstile хост `trycloudflare.com` у списку доменів віджета, невідомо).
- **Ліміти:** до 200 акаунтів (`SB_MAX_PUBLIC_USERS`, до 2026-10-26 було 25; квота 3 ГБ на акаунт, тож при заповненні всіх місць диск може не вистачити: стежити за `df`); 8 реєстрацій на годину з однієї адреси; 8 невдалих входів на ім'я й 12 на адресу за 15 хвилин (потім 429); 6 змін пароля за 15 хвилин; один пароль не менше 10 символів і не надто простий. Ліміти лежать у пам'яті й скидаються рестартом сервісу. Завантаження: до 90 МБ за раз (Cloudflare не пропускає запити понад 100 МБ; фото стискаються в браузері до 2400 пікселів), до 3 ГБ даних на акаунт, до 20 завантажень у черзі, не більше 6 одночасних входів у Claude.
- **CSRF:** будь-який запис без `Origin` свого сайту відхиляється (403), плюс SameSite=Strict. JSON більше 1 МБ відхиляється до читання.
- **Читання без акаунта (2026-10-26):** без сесії (немає cookie, зіпсований чи прострочений) публічний екземпляр показує **головну книгу** (бібліотеку першого адміна) лише для читання: `/api/status` віддає знеособлений знімок (`anon_status`: предмети, книги, розділи, білети, інтерактивні сторінки; без логіну, черги, запитів, пропозицій, двигуна, помилок), а `/books/…`, `/exams/…`, `/i/…` віддають файли головної книги. Це працює і для посилання, відкритого з месенджера: cookie `SameSite=Strict` при переході зі стороннього сайту не надсилається, тож такий клік завжди веде в головну книгу. Будь-який запит, що щось міняє (`who()`), відповідає 401, і сторінка відкриває вікно входу/реєстрації (його можна закрити, поки це режим читання). Ліміт 240 запитів/хв на адресу, снапшот статусу кешується на 3 с.
- **Заголовки сторінки:** CSP (`default-src 'none'`, дозволено лише скрипти сторінки й Cloudflare), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`. Інтерактивні сторінки `/i/…` лишаються в CSP-пісочниці.
- **Пароль:** `accounts.json` (0600) зберігає лише сіль і scrypt-хеш. Забутий пароль скидає адмін на вкладці «Адмін» (видає тимчасовий; людина змінює його в «Книги → Акаунт»). Там же вимкнути акаунт або «вийти скрізь» (усі старі cookie вмирають, бо змінюється версія сесії).
- **Вимкнути публічний доступ:** `systemctl --user stop studybooks-tunnel` (адреса вмирає одразу). Назавжди: `systemctl --user disable --now studybooks-tunnel` і `sudo systemctl disable --now studybooks-public`.
- **Дані й доступ:** публічні люди живуть в тому самому `data/users/` (`pub-…`), їхні матеріали обробляються їхньою власною підпискою Claude або ключем OpenRouter. Їхні пропозиції «в основну книгу» потрапляють до адміна так само, як у друзів із tailnet.
- **Тест:** `tests/test_public.py` (90+ перевірок: підроблений заголовок Tailscale, перевірка «людина» й повтор розв'язку, реєстрація, cookie, блокування, підроблені й прострочені сесії, CSRF, ізоляція просторів, ліміти завантажень, Turnstile з фейковим Cloudflare, адмін-інструменти на tailnet-екземплярі). Окремо перевірено у справжньому браузері (реєстрація через воркер, з реальним CSP) і через справжній тунель Cloudflare (реєстрація, вхід, підроблений заголовок = 401, адмінка = 403).

### Розділи за датою заняття (додано 2026-10-21)

Книга більше не ділиться на теми. **Розділ = день, коли відбулося заняття**, і саме цю дату людина ставить при завантаженні.

- **Форма «Додати»:** поле «Дата заняття» (за замовчуванням сьогодні, не пізніше за сьогодні, не старіше 3 років; для «Підручника для звірки» поля немає). Під ним видно, чи є вже щось у книзі за цю дату («буде новий розділ» або «піде в той самий розділ як доповнення»). Після відправки дата скидається на сьогодні, щоб наступне завантаження не потрапило у старий день.
- **Доповнення до минулого заняття** = завантаження з датою цього заняття. Воно лягає в той самий розділ окремим записом, у кінець розділу (за часом завантаження). Біля такого запису в обох книгах стоїть «added later, <коли додано>». Claude у промпті бачить, що вже є за цей день (`{{same_day}}`), тому називає запис як продовження («Lecture 3 (continued): …») і не повторює вже наявного.
- **Зміна дати вже наявного запису:** на вкладці «Книги» розгорни «Заняття за датами» біля предмета, у кожного запису є поле дати. Це `POST /api/entry/date` (`subject`, `topic`, `entry`, `date`): змінює лише `meta.json`, папка запису лишається, книга й вижимки двох зачеплених днів перебудуються.
- **Дані:** `meta.json` запису має `date` (`YYYY-MM-DD`), `submission.json` теж. Записи без `date` (усе, що завантажене до цієї зміни) вважаються проведеними в день завантаження (`added`). Дату для них можна виправити в тому ж списку.
- **Порядок:** розділи від старішої дати до новішої; записи в розділі за часом завантаження. Назва розділу — «Wednesday, 14 October 2026», у змісті й у посиланнях «(Ch. …)» словника так само.
- **Тема** лишається міткою запису (її далі вибирає Claude, для PDF без редагування вибирає людина). Вона показується в рядку «Lecture · тема» під заголовком запису і у списку змін дати. Пояснення й інтерактивні сторінки прив'язані до теми, тому лягають у **найпізніший розділ цієї теми**; якщо запису з такою темою ще немає, то в розділ того дня, коли їх зроблено.
- **Вижимка й словник тепер на день заняття:** `library/<предмет>/_days/<дата>/_digest/` (раніше на тему). `DIGEST_VERSION` = 2, промпт `digest.md` говорить про «chapter = one class day». Після зміни дати вижимки зачеплених днів перегенеруються самі (по одному короткому текстовому виклику Claude на день). Старі теки `<тема>/_digest/` більше не читаються.
- **Тест:** `tests/test_days.py` (55+ перевірок: дата й помилки, завантаження через API, повний прохід воркера з фейковим Claude, порядок і розділи, доповнення в той самий розділ, вижимки по днях, обидві книги в Typst, статус, зміна дати й захист від `../`, запис без дати, пояснення, промпт).

### Білети до екзамену — третя вкладка «Білети» (додано 2026-10-21)

Claude складає **набір екзаменаційних білетів** з тексту обраних занять. Запит іде тією самою чергою, що й пояснення (`requests/`, `kind: "exam"`), працює двигуном цієї людини.

- **Форма:** предмет; заняття, з яких брати питання (за замовчуванням усі, де є текст; PDF «як є» без тексту вимкнені); скільки білетів (1–30); питань у білеті (1–5); склад (теорія й задачі / лише теорія / лише задачі); складність (легше / як на заняттях / складніше); мова білетів (англійська, німецька, українська); побажання (до 400 символів, це лише побажання, а не інструкції).
- **Склад «теорія й задачі»:** 1 задача на білет при 2–3 питаннях, 2 при 4–5, а при одному питанні білети чергуються. Теорія йде першою.
- **Результат:** `exams/<предмет>/<id>/{tickets.pdf, answers.pdf, tickets.json, meta.json}`. `tickets.pdf` — один білет на сторінку з рядком «Name», для друку; `answers.pdf` — ті самі білети, під кожним питанням еталонна відповідь у зеленій рамці й «з якого заняття» питання. Закладки PDF = білети.
- **Як працює:** `process_exam()` кладе в `work/context/<дата>/` тексти записів (`clean.md`) і вижимки днів, Claude читає їх і підручники для звірки та пише **один файл `tickets.md`** (`prompts/exam.md`). Формат із маркерами (`=== TICKET n ===`, `--- QUESTION | theory|problem | дата ---`, `--- ANSWER ---`), а не JSON: LaTeX не треба екранувати.
- **Перевірки в коді** (`parse_tickets`, `validate_tickets`, `load_tickets`), що б Claude не відповів: точна кількість білетів і питань, склад (скільки задач), нумерація, непорожні питання й відповіді, без дубліката питання, без зображень, посилань і веб-адрес, довжина ≤ 6000 символів. Якщо щось не так або не збирається Typst, **один** виправний виклик (`prompts/exam_fix.md`); якщо й після нього структура хибна, запит падає й повторюється як звичайний (до 3 спроб). Окрема формула, яку не вдалося полагодити, лишається текстом (`raw`), решта набору збирається. Дата питання не з обраних занять мовчки відкидається.
- **Сторінка білета:** після збірки PDF читається назад (`pymupdf`) і для кожного білета записується його сторінка (`meta.pages`), бо білет може займати більше однієї сторінки. На цьому тримається кнопка **«Витягнути білет»**: випадковий білет **без повторів** (як на екзамені, стос перемішується знову, коли білети скінчилися; витягнуті пам'ятаються в браузері, `localStorage.exdrawn`), а потім «Відкрити білет» і «Відповіді до нього» відкривають PDF одразу на потрібній сторінці (`#page=N`). Видалення набору потребує другого кліку.
- **Ліміти (на людину):** не більше 2 запитів у черзі, 8 на добу, 20 наборів на предмет. Кожен набір це один довгий виклик Claude (30 білетів × 5 питань з відповідями можуть бути довгі), тому для щоденної роботи краще 5–15 білетів.
- **Ендпоінти:** `POST /api/exam` (`subject`, `days`, `tickets`, `per`, `mix`, `level`, `lang`, `text`), `POST /api/exam/delete` (`subject`, `id`), `GET /exams/{subject}/{id}/{tickets|answers}.pdf` (лише власнику простору). Статус віддає `subjects[].exams` і `exam_limits`. Публічний екземпляр має ті самі ендпоінти під власним входом.
- ⚠️ **Відповіді пише модель.** Вони перевірені лише тим, що Claude мав підручники для звірки, а не окремою звіркою. Тексти задач і чисел варто перевіряти самому (у вкладці це сказано).
- **Тест:** `tests/test_exam.py` (90+ перевірок: запит і ліміти, формат і всі перевірки, виправний прохід, збій і повтор, сторінки білетів у PDF, мови PDF, ендпоінти, ізоляція людей, видалення) і `tests/check_page_dict.js` (словник сторінки: 3 колонки, дублі, кирилиця в англійській колонці, усі використані ключі існують; `node tests/check_page_dict.js`). Сторінку перевірено в headless Chrome з підставним статусом: вибір днів, надсилання, жеребкування, двокрокове видалення, перемикання мови.
- Не перевірено на справжньому Claude: якість і правильність справжніх білетів і час складання великого набору.

### Мови: українська й англійська (додано 2026-10-20)

Перемикач `UK | EN` у шапці сайту. Вибір пам'ятається в браузері (`localStorage.lang`), а за замовчуванням береться з мови браузера: `uk`, `ru`, `be` дають українську, усе інше англійську.

- **Сторінка (`web/index.html`):** один словник `D`, де кожен рядок має вигляд `[ключ, українська, англійська]`. Рядки з підстановками записані функціями, форми множини (`pl.*`) масивами. Статична розмітка береться з `data-i18n`, `data-i18n-html`, `data-i18n-ph`, `data-i18n-label`, а динамічні рядки з `t("ключ", …)`. Дата й час форматуються за мовою (`uk-UA` / `en-GB`). Кожен запит несе заголовок `X-Lang`.
- **Сервер (`sb.py`, `web.py`):** усе, що може прочитати людина, обгорнуто в `L(укр, англ)`. Мова береться з `contextvars`: `web.who()` встановлює її для запиту (заголовок `X-Lang`, інакше мова, збережена в профілі, поле `lang` у `profile.json`), а воркер встановлює мову людини, чию чергу обробляє (`set_lang(sp.lang())`). Тому помилки API, пояснення відмов, причини, паузи, `blocked`, стани злиття й підписи в `status()` приходять мовою читача. Тексти, записані воркером у файли даних (наприклад, `reason`, `last_error`), лишаються мовою, якою їх було написано на той момент.
- **Відповіді Claude/OpenRouter** (`reason` пропозицій і аналізу) пишуться мовою читача: промпти `suggest.md` і `merge.md` отримують `{{lang_name}}`.
- Не перекладено: тексти самих книг (вони англійські, оригінал мовою джерела), назви предметів із `syllabus`, технічні логи й дані, що ввела людина.
- **Правило для змін:** кожен новий видимий рядок додавай у **обидві** мови: рядок у таблицю `D` (сторінка) або `L(…, …)` (сервер). Тест `tests/test_i18n.py` (25 перевірок) і перевірка словника (ключі, кирилиця в англійській колонці) описані в `CLAUDE.md`.

### Двигун: Claude або OpenRouter, вибір для кожної людини (додано 2026-10-20)

Кнопка вгорі справа («Claude: …» / «OpenRouter: …» / «Налаштувати двигун») відкриває діалог із двома вкладками. За замовчуванням усі на Claude, і нічого не змінилось для тих, хто нічого не обирав.

- **Claude Code** (як було): `run_claude_cli` запускає `claude -p` із власним входом людини.
- **OpenRouter:** `run_openrouter` у `sb.py` сам веде цикл агента через `POST {OPENROUTER_URL}/chat/completions` з tool calling. Інструменти моделі: `read_file` (текст, а фото й сторінки як зображення в наступному повідомленні), `write_file`, `edit_file`, `grep`, `glob`. Вони обмежені робочою папкою запуску (підручники для звірки лише читання), символічні посилання й `..` не пускають назовні. Помилки інструментів повертаються моделі текстом. Ліміт 120 кроків і 40 хв.
- Усі виклики йдуть через `run_llm(sp, …)`, яка бере двигун із `profile.json` (`engine`, `openrouter_model`). Однакові промпти, однакові перевірки (`validate_change`, Typst), тож пропозиції, вижимки, пояснення, злиття й завантаження працюють на будь-якому двигуні. Аналіз для адміна йде двигуном **адміна**, пропозиція людини двигуном **цієї людини**.
- **Ключ:** кожен вставляє свій ключ OpenRouter (`sk-or-…`). Сайт перевіряє його запитом `GET /key`, пише у `users/<uid>/openrouter.key` із правами **0600** (не в `profile.json`, не в git) і ніколи не повертає назад, лише останні 4 символи. Не більше 10 спроб на годину. Це не те саме, що токен claude.ai: ключ OpenRouter створений саме для використання застосунками. Правило «ніколи не збирати токени claude.ai» лишається в силі.
- **Моделі:** список беремо наживо з `GET /models` (кеш 1 год у `data/state/openrouter-models.json`), лише ті, що вміють `tools`. Біля моделі видно ціну за 1M токенів, контекст і чи вона бачить зображення. Модель **без зору** можна обрати (для вижимок, пояснень, пропозицій), а завантаження з фото чи PDF-сторінками вона відхилить з поясненням.
- **Помилки:** 401/403 → пауза «не прийняв ключ», 402 → пауза «закінчились кредити», 429/5xx/мережа → дві повторні спроби й пауза до наступного запуску. Блок і повтор такі ж, як у Claude.
- Ендпоінти: `GET /api/openrouter/models`, `POST /api/engine` (`engine`, `model`), `POST /api/openrouter/key`, `POST /api/openrouter/key/remove`, `GET|POST /api/openrouter/free`, `POST /api/openrouter/free/reset`. Для тестів `SB_OPENROUTER_URL` підміняє адресу API.
- **Автоматичний режим безкоштовних моделей** (модель `auto:free`, кнопка «Автоматично: усі безкоштовні моделі»):
  - **Порядок («найкраща» спершу):** безкоштовні моделі з інструментами (зараз 16; `openrouter/free` і ті, що зникнуть за 2 доби, пропускаються). Оцінка `or_quality`: `intelligence_index + 0.5·agentic_index` із бенчмарків OpenRouter (`benchmarks.artificial_analysis`); якщо бенчмарка немає, груба оцінка за розміром з назви (`4·log2(1+B)`, максимум 22), інакше 10. У діалозі видно джерело оцінки, а порядок і вимкнення моделей можна змінити вручну (`or_free_order`, `or_free_exclude` у профілі).
  - **Перемикання:** `run_openrouter` бере найкращу доступну. На 429 (ліміт), 5xx, 400/404 (модель не вміє інструментів чи її прибрано), порожню відповідь або обірвану відповідь модель паркується, а **наступна продовжує ту саму розмову** (без `reasoning_details` попередньої). Якщо модель завершила, нічого не записавши, наступна починає з чистого аркуша. Для завдань із фото беруться лише моделі зі зором, а також ті, чий контекст вміщає розмову.
  - **Паузи (`users/<uid>/or_state.json`):** 429 → `Retry-After` або `X-RateLimit-Reset`, інакше експоненційно 65 с … 1 год; 5xx → 5 хв; 404/400 → 30 хв; без запису → 10 хв. **Добовий ліміт** (заголовок `X-RateLimit-Limit` 50/1000 або «per-day» у тексті) паркує **всі** безкоштовні моделі до відновлення (або до 00:00 UTC). Коли пауза на всіх, воркер не робить жодного запиту, ставить людину на паузу з повідомленням «відновиться о HH:MM» і повторює наступним запуском. Кнопка «Зняти паузу» (`/free/reset`), наприклад після поповнення.
  - **Ліміти OpenRouter:** 20 запитів за хвилину (між запитами пауза 3,2 с) і 50 на добу, або 1000, якщо коли-небудь поповнено ≥$10 (за `/credits`, якщо ключ дозволяє; інакше лічильник без цифри). Документація не каже, чи добовий ліміт спільний для всіх моделей; код керується відповіддю API.
  - **Чесні застереження** показано в діалозі: слабші моделі, 50 запитів на добу швидко вичерпуються агентним циклом, а умови зберігання даних визначають безкоштовні провайдери.
  - Будь-який двигун OpenRouter тепер вважає помилкою «модель закінчила, нічого не записавши» (раніше це давало тиху «успішну» відповідь і пізнішу помилку про відсутній файл).
- Тест: `tests/test_openrouter.py` з `tests/fake_openrouter.py` (понад 70 перевірок: ключі, інструменти й обмеження, цикл, помилки, змішані двигуни людина/адмін, текстова модель + фото, відсутній ключ, і весь режим `auto:free`: рейтинг, перемикання посеред завдання, добовий ліміт, усі на паузі, 404, 500, порожня відповідь, зір, ручний порядок, проміжок між запитами).
- ⚠️ Не перевірено на справжньому OpenRouter із ключем (тільки список моделей і відхилення неправильного ключа). Якість роботи залежить від моделі: ліпше обирати сильні моделі з візією.

### Пропозиції доповнень і злиття в основну книгу (додано 2026-10-20)

**Основна книга = бібліотека адміна.** Адмін: `SB_ADMIN` у `.env` (за замовчуванням `owner-example-com`, можна кілька через кому; основною є бібліотека першого).

```
людина ──► «Запропонувати доповнення» (запис книги або інтерактивна сторінка) ──► suggestions/<id>/s.json
              │  Claude ЛЮДИНИ (її логін) вирішує: accept / partial / reject, чернетка в work/, не в бібліотеці
              │  код перевіряє чернетку (validate_change + збірка в Typst) → тільки тоді пишеться в її книгу
              ▼  якщо людина дозволила (галочка) і не вичерпані ліміти
        data/merge/<id>/c.json  ──► Claude АДМІНА порівнює з сторінками основної книги (prompts/merge.md)
              │  verdict: merge / duplicate / conflict / offtopic / nomatch / unverified; чернетка, теж через validate_change
              ▼
        вкладка «Адмін»: diff → [Злити] / [Відхилити] / [Скасувати злиття] / [Проаналізувати ще раз]
              ▼  «Злити» перевіряє sha сторінки (змінилась після аналізу → відмова), пише, git commit, mark_dirty → книга й вижимка перебудуються
```

- Пропозиції є тільки до сторінок із текстом: записи (`clean.md`) й інтерактивні сторінки. PDF без редагування не підходять. `original.md` не змінюється ніколи.
- Вхід: `POST /api/suggest`, `POST /api/suggest/{id}/undo`. Адмін: `GET /api/admin/merge`, `POST /api/admin/merge/{id}/{merge|decline|undo|reanalyze}`, `POST /api/admin/merge/state` (`paused`, `uid`+`block`). Адмін-ендпоінти дають 403 всім, крім `SB_ADMIN`.
- Дані: `users/<uid>/suggestions/<id>/{s.json, before.*, after.*}`, глобально `data/merge/<id>/{c.json, before.*, after.*}` і `data/merge/state.json` (пауза, заблоковані).
- Власні пропозиції адміна застосовуються просто до його книги, без черги.

**Захист від зловживань (багатошаровий):**
1. **Ліміти на людину:** до 5 пропозицій на добу, до 3 в очікуванні, 20 с між ними, одна в очікуванні на сторінку, дубль того ж тексту за 14 днів відхиляється, текст 15–1500 символів (без керівних символів, «спам» з кількох літер відхиляється). Після 4 відхилень з останніх 6 пауза 6 год. Збої системи (`failed`) у ліміт не рахуються. Гонку двох запитів блокує `flock`.
2. **Текст пропозиції = недовірені дані.** У промптах (`suggest.md`, `merge.md`) прямо сказано, що це не інструкції, а спроба керувати Claude означає відхилення. Claude працює лише з Read/Write/Edit/Grep/Glob у тимчасовій папці й не пише в бібліотеку.
3. **Перевірка коду над чернеткою Claude** (`validate_change`), що б Claude не відповів: для Markdown лише невелике доповнення (≤80 рядків, ≤6000 символів, ≤15% наявного тексту змінено), без HTML, посилань, зображень, raw-атрибутів і нових `{{fig:…}}`; для HTML ≤250 рядків, без `fetch`/XHR/WebSocket/`eval`/`Function`/сховища/cookie/навігації/iframe/form/link/meta, без зовнішніх `src`/`href`/`url()` і `@import`. Markdown ще й мусить зібратися в Typst. Усе перевірено на ~40 прикладах (чисті й зловмисні).
4. **CSP для `/i/…`:** `sandbox allow-scripts; default-src 'none'; connect-src 'none'; form-action 'none'` і т. д. Сторінка в опаковому origin без мережі: навіть якщо скрипт прослизне, він не викличе `/api/*` і нічого не надішле назовні. Це ж закрило наявну діру: раніше такі сторінки віддавались без CSP з того самого origin.
5. **Згода й межі злиття:** до адміна йде тільки за галочкою. Не більше 3 на людину на добу й 30 у черзі в цілому. Адмін може призупинити приймання або заблокувати людину. Аналіз ніколи не змінює книгу, змінює тільки клік адміна.
6. **Зворотність:** `before.*`/`after.*` зберігаються, undo перевіряє sha (чужі правки зверху не затираються), git-коміт на кожну зміну.

Тести: `tests/test_suggest.py` (офлайн, з `tests/fake_claude.py`, на копії коду з `SB_DATA=/tmp/…`; 40+ перевірок: валідація, повний шлях людина→адмін→злиття→undo, зловмисні чернетки, ліміти, пауза/блок, застарілий sha).

### Економія ліміту при багатьох завантаженнях (додано 2026-10-25)

Причина: 21–24.10 сім завантажень `pub-guest` (одне — 10 файлів = 16 порцій) йшли по черзі, кожна порція — opus на 25–35 ходів із зображеннями й самостійним пошуком у підручниках, і ліміт закінчувався посеред черги. До того ж відмову «You've hit your session limit» код не впізнавав як ліміт: кожне наступне завантаження все одно пробувало, отримувало ту саму відмову й рахувало спробу (21.10 так пішли в «невдалі» 9 завантажень).

| # | Що | Як |
|---|---|---|
| 1 | **Зупинки на 70 / 80 / 90 %** | `Space.limit_gate()` дивиться на `claude_usage.json` (те, що Claude Code сам повідомив у `rate_limit_event`). Коли будь-яке вікно (5 год, тиждень, …) перейшло наступний поріг, `run_llm` кидає `LimitGateError` (підклас `TransientError`): елемент лишається в черзі без спроби, `blocked` не пишеться. Сторінка показує банер і кнопку «▶ Продовжити» → `POST /api/limit/continue` → `ack_limits()` запам'ятовує поріг для кожного вікна (`limit_ack` у профілі, разом із часом скидання: нове вікно = пороги знову). `kick` не будить воркер для такої людини (крім PDF без редагування). Тільки для Claude: у OpenRouter свої ліміти. |
| 2 | **Моделі за роллю** | `ROLE_MODELS`: транскрипція, вижимки, `fix` — sonnet; пошук у підручниках і карти — haiku; чистий текст, пояснення, білети, злиття — модель людини. Модель людини — стеля (хто вибрав haiku, усе на haiku). `SB_MODEL_<РОЛЬ>` у `.env` міняє одну роль. `--effort` іде лише з власною моделлю людини. `ROLE_TURNS` обмежує ходи (60/40/40/30/15 замість 120). |
| 3 | **Пошук у підручниках — окремий дешевий прохід** | `run_refs_pass`: haiku читає транскрипцію, карту книги і лише потрібні сторінки (≈12), пише `refs_notes.md` з точними формулюваннями й сторінками. Прохід чистого тексту вже не має доступу до підручників, а бере `refs_notes.md`. Невдача тут не фатальна. Немає книг для предмета — виклику немає. |
| 4 | **Друковані сторінки — лише текстом** | `text_is_enough()`: сторінка PDF із ≥200 символів тексту, без картинок, більших за логотип (3 % площі), ≤15 векторних елементів і майже без математичних символів іде моделі як `text/pNNN.txt (typed page, text only)`. Зображення все одно зберігається для `original.pdf`. Сторінки з формулами, графіками, фото — як і раніше з картинкою. Зменшувати роздільність немає сенсу: Claude сам стискає картинку до ≈1,15 Мп, понад ≈1600 токенів вона не коштує. |
| 5 | **Групи й порядок** | `upload_group`: завантаження «навчальний матеріал» з однаковою підказкою предмета й датою заняття, разом до 12 сторінок, обробляються одним викликом на прохід. ### Модель і effort Claude, кнопка «Зупинити» (додано 2026-10-24)

- **Модель і effort для кожної людини:** у діалозі двигуна, вкладка Claude, два списки: модель (`opus`/`sonnet`/`haiku`/`fable`, або «за замовчуванням» = `SB_MODEL`) і effort (`low`…`max`, або типовий Claude Code). `POST /api/claude/settings` пише `claude_model`/`claude_effort` у `profile.json` лише зі списків `CLAUDE_MODELS`/`CLAUDE_EFFORTS` (інше → 400; сміття в профілі → типові значення), `run_claude_cli` додає `--model` і `--effort`. Діє з наступного виклику Claude. OpenRouter має свій вибір моделі; effort там не передається.
- **«⏹ Зупинити» в шапці** (видно, коли є черга або щось працює для цієї людини): `POST /api/stop` ставить `paused: true` у профіль. Воркер дивиться на цей прапорець кожні 2 с під час виклику Claude (Claude Code працює у власній групі процесів, `kill_group`: SIGTERM, через 10 с SIGKILL), а OpenRouter — перед кожним наступним запитом (уже надісланий запит доходить до кінця, до 5 хв). Виклик кидає `StoppedError` (це `BaseException`, тож обробники помилок її не ловлять): елемент **лишається в черзі, спроба не рахується**. Поки пауза, воркер не бере нічого з черги цієї людини й не пише вижимки (збірка вже готових PDF іде), `kick` не будить воркер лише заради такої черги. «▶ Продовжити» = `POST /api/resume` + `kick`. Інших людей пауза не зачіпає.
- Завантаження продовжується з місця зупинки: готові частини (`c<N>/.done`) не переробляються, перервана частина робиться наново.
- Тест: `tests/test_stop.py` (35 перевірок: аргументи CLI, відмова чужих значень, зупинка повільного фейкового Claude за секунди й смерть процесу, воркер пропускає паузу й обробляє іншу людину, зупинка елемента воркера без спроби, продовження, OpenRouter). Для нього `fake_claude.py` отримав `FAKE_ARGS` і `FAKE_SLEEP`. Вигляд перевірено в headless Chrome (діалог, робота, пауза).

### Usage bar під кнопкою двигуна (додано 2026-10-21)

Під кнопкою «Claude: …» у шапці стоять тонкі смужки лімітів.

- **Claude:** «5 год» і «тиждень» (за наявності ще Opus/Sonnet): смужка й відсоток, жовта від 75%, червона від 95% або коли ліміт вичерпано («вичерпано», внизу час скидання). Підказка при наведенні: час скидання й коли дані оновлено. Поки Claude нічого не повідомив, стоїть «Ліміти з'являться після першої обробки».
- **Звідки дані:** `run_claude_cli` тепер запускає `claude -p --output-format stream-json --verbose` і читає з потоку події `rate_limit_event` (а також `rate_limit_info` у відмові через ліміт). Остання `result`-подія дає ту саму відповідь, що давав `json`, старий однорядковий формат теж розбирається (`parse_claude_output`). Дані лежать у `users/<uid>/claude_usage.json` (лише `status`, `resets`, `util`, `overage`, `seen`), тому бар оновлюється **після кожної обробки, а не в реальному часі**. Вікно, чий час скидання минув, відкидається.
- **Чого я не роблю:** не беру токен людини й не ходжу з ним на `/api/oauth/usage` (так робить сам `/usage` у Claude Code, але для стороннього застосунку це заборонено). Окремого офіційного запиту «скільки лишилось» без виклику моделі немає.
- ⚠️ **Не перевірено на справжньому Claude** (користувач відмовився від проби): невідомо, чи `rate_limit_event` завжди містить `utilization`. За документацією бінарника поле необов'язкове, а відсоток могли показувати лише біля порога. Тоді замість смужки видно «ок» і час скидання. Перший справжній прогін покаже, що саме приходить (`cat users/<uid>/claude_usage.json`).
- **OpenRouter:** для режиму `auto:free` смужка «запитів сьогодні N/ліміт» (лічильник у `or_state.json`, без мережевих запитів), пауза до часу, якщо вичерпано добовий ліміт. Для однієї обраної моделі бару немає.
- Тест: `tests/test_usage.py` (27 перевірок: потік, старий формат, сміття, нормалізація, збереження числа в тому самому вікні, відкинуте вікно, ліміт 4 рядки, файл без токенів, повний виклик через фейковий CLI, OpenRouter). Вигляд перевірено в headless Chrome у чотирьох станах.

### Індикатор активності біля книги (додано 2026-10-20)

На вкладці «Книги» біля кнопок книги з'являється спінер з підписом, поки з цим предметом щось відбувається: «Claude розбирає завантаження», «Claude пише вижимку розділу», «Claude пише пояснення», «Додається PDF», «Книга збирається, зараз файл може бути старим» і сіра пульсуюча крапка «У черзі на обробку». Для завантаження з автовизначенням предмета індикатор стоїть над списком книг, а коли предмет відомий, переходить на його книгу.
- Воркер пише в `state/status.json` поля `current_subject`, `current_phase` (`ingest`/`asis`/`request`/`digest`/`build`) і `build_pending` (предмети, що чекають збірки). `status()` віддає `activity` для кожного предмета й `auto_activity`.

### Вижимка й словник (додано 2026-10-16)

- **Окремий виклик Claude на розділ (день заняття)**, тільки текст `clean.md` усіх записів цього дня, без фото. Отже, одне завантаження → +1 короткий виклик на кожен день, який воно зачепило (з 2026-10-21 розділ = день, раніше = тема).
- **`summary.md`** — стиснена вижимка (≈1/5 розділу, максимум ~2 сторінки). Секції: Definitions / Results / Formulas / Methods / Watch out. Нічого нового понад матеріал. У `clean.pdf` вона стоїть у зеленій рамці «Chapter summary» в кінці розділу.
- **`glossary.json`** — `[{term, definition}]` англійською. У кінці `clean.pdf` терміни всіх розділів об'єднуються, дублікати зливаються, усе сортується за алфавітом із буквами-розділювачами. Біля кожного терміна стоїть клікабельне «(Ch. 1, 2)».
- **Як визначається застарілість:** `meta.json` зберігає sha1 від (назви записів + `clean.md` + `DIGEST_VERSION`). Якщо sha не збігається, вижимка застаріла, і `kick` сам запускає воркер. Після зміни `prompts/digest.md` треба збільшити `DIGEST_VERSION` у `sb.py`, тоді всі вижимки перегенеруються.
- **Збої:** лічильник у `data/users/<uid>/digest_failures.json`. Після 3 невдач на тому самому вмісті тема більше не повторюється, а сайт показує «Вижимка розділу … не вийшла». Новий запис у темі змінює sha і скидає лічильник. Ліміт або вихід із Claude ставить людину на паузу, як і для завантажень.
- Якщо визначення в словнику має битий TeX, pandoc друкує його як текст, і книга все одно збирається.
- `original.pdf` вижимки й словника не має.

**Двигун:** Claude Code (`~/.local/bin/claude -p`) з інструментами тільки Read/Write/Edit/Grep/Glob і `--add-dir` на довідкові підручники. Модель задається через `SB_MODEL` у `~/studybooks/.env` (за замовчуванням `opus`).

### Кілька користувачів

Кожна людина має свою окрему бібліотеку й **свій власний вхід у Claude**:

- `uid` = slug заголовка `Tailscale-User-Login`. Власник: `owner-example-com`.
- `data/users/<uid>/` містить inbox, processed, failed, work, library (git), books, build, refs, requests, syllabus, а також `claude/`, яка є `CLAUDE_CONFIG_DIR` цієї людини.
- Кнопка на сайті **«Підключити Claude»** запускає незмінений `claude auth login --claudeai`. Він показує посилання, людина вставляє код від Anthropic, і облікові дані зберігає сам Claude Code.
- ⚠️ **Ніколи не додавати поле «вставте свій токен».** Правила Anthropic для Claude Code забороняють застосунки, які збирають або зберігають токени claude.ai. Водночас дозволено, щоб людина сама входила своєю підпискою в незмінений бінарник.
- Воркер пропускає людей, які не увійшли в Claude або вперлися в rate-limit.
- Спільні відкриті підручники лежать у `data/refs-open/`.

### Спільна книга (додано 2026-10-26)

Книги й інтерактивні сторінки **бачать усі однакові**: головна книга (бібліотека першого адміна) для кожного, хто ввійшов або читає без входу. Своїх книг у людей більше немає в переліку.

- **Читання:** `viewer()` в `web.py` віддає головну книгу всім (і в tailnet, і на публічному екземплярі). Це `/books/…`, `/i/…`. `/api/status` для всіх, крім власника, має `shared: true`, а предмети, книги, розділи й інтерактивні сторінки беруться з головної книги (`shared_view()`). Власні черга, вхід у Claude, двигун, ліміти, білети (`exams`), «що робиться» і посилання на підручники лишаються людині.
- **Запити на пояснення й інтерактивні сторінки від будь-кого** пишуться **у головну книгу без підтвердження** (`shared_target()` у `sb.process_request`): модель працює на логіні того, хто запитав (`sp`), а файл і `syllabus` йдуть у бібліотеку адміна (`tgt`). У метаданих сторінки є `by: <uid>` (власник сам не має `by`). Вигляду «запит → лише для нього» більше немає.
- **Власні завантаження** людини, як і раніше, йдуть у її простір і обробляються її логіном. У спільну книгу вони НЕ потрапляють (вирішення окреме: див. «Відкрито»). Її книги в «Книгах» не видно.
- **Дати записів** гість не змінює: поле дати в «Заняття за датами» сховане, а `/api/entry/date` шукає запис у просторі самої людини, тож чужий запис дає помилку, а не змінюється. Видалення спільних записів у сайті не передбачено. Пропозиції доповнень для спільних сторінок вимкнено (`targets: []`), бо їхні цілі вказували б у чужий простір.
- **Тест:** `tests/test_shared.py` (гість пише пояснення → лягає в головну, `by`, статус `shared`) + оновлені перевірки в `test_public.py` (гість бачить головну книгу).

**Відкрито:** (1) ~~завантаження гостя лягають у його власну бібліотеку~~ — з 2026-10-26 (вечір) усі завантаження йдуть у спільну книгу, див. нижче. (2) Гість може створити сторінку в спільній книзі без перевірки. Текст лишається недовіреним, а `/i/…` ізольовано CSP, але модерації немає. (3) Пропозиції й злиття з боку гостя тимчасово вимкнені.

### Спільні завантаження і злиття тієї самої лекції (2026-10-26)

- **Куди:** кожне завантаження (навчальний матеріал і «PDF без редагування») обробляється логіном/двигуном того, хто завантажив, а записи лягають у **спільну книгу** (`shared_target(sp)`; для власника це його ж `Space`, тож `tgt is sp` = «моя книга»). У `meta.json` запису є `by: <uid>`; запис без `by` належить власнику бібліотеки (`entry_by()`). Підручники (`kind: reference`) лишаються особистими. `submission.json` в `processed/` людини має `library`, `fused`, `joined`.
- **Розпізнавання лекції:** прохід транскрипції отримує `{{existing}}` (`lecture_candidates()`): записи спільної книги того самого предмета (або всіх, якщо предмет не вказано) у межах ±14 днів від дати заняття, з id `subject/topic/entry` і початком тексту. Модель ставить `same_as`, коли це те саме заняття. Код перевіряє (`same_lecture()`): id існує, той самий предмет, не `_`-тека.
- **Злиття (`fuse`):** окремий прохід (`prompts/fuse.md`, роль `fuse` → sonnet) пише `merged_clean.md` з `old_clean.md` + `new_clean.md`. Код приймає злиття лише якщо: текст не коротший за 85 % старого, всі `{{fig:…}}` старого на місці, формул не менше 85 %, типографується (один виклик `fix`, **ніколи** не сирий фолбек цілої лекції). Тоді `fuse_apply()`: новий `clean.md`, у `original.md` дописується «Supplement, added …» з новою транскрипцією, нові сторінки й фігури з префіксом `x<hash>` (щоб id не збіглися), `contributors: [{by, at, submission, title, added}]`, `updated`. Перед записом звіряється sha старого `clean.md` (змінився → не зливати). Невдале злиття = окремий запис **на дату розпізнаної лекції** (`date_given` = дата, яку дала людина). Усі виклики моделі робляться до першого запису в бібліотеку (повторний запуск продовжує з маркерів).
- **Хто додав:** статус дає `by_name` (ім'я з профілю першим словом або логін без домену, ніколи e-mail), `with` (хто доповнив), `mine`. Сирий uid назовні не йде (`shared_view` прибирає `by`), анонімам (`anon_status`) ці поля не віддаються. У PDF імен немає.
- **Дата:** `/api/entry/date` працює по спільній книзі; власник змінює будь-який запис, інші — лише ті, де `by` = вони (403 інакше).
- **Дублікати між людьми:** `find_duplicate` дивиться ще й `file_hashes.json` інших просторів; відмова 409 називає, хто вже завантажив.
- **Перенесення 2026-10-26:** 65 записів, що раніше скопіювали з `pub-guest`, отримали `by: pub-guest` (коміт «by: mark the entries merged from pub-guest»).

### OpenRouter: хто заплатив і 403 однієї моделі

- **Оплата:** `or_paid()` питає `GET /key` (`is_free_tier`), запасний шлях `/credits` (`total_credits ≥ 9`). `or_refresh_tier()` пише `or_paid`, `or_daily_cap` (1000 або 50), `or_tier_at`; повторно не частіше ніж раз на 6 год, але одразу, якщо запитів сьогодні більше за 50 при ліміті 50, при добовому 429, і при відкритті списку моделей (раз на 10 хв). Раніше ліміт визначався лише раз, коли вводили ключ, звідси «101/50».
- **403:** `_or_error` → `OrForbidden` (підклас `AuthError`). У режимі `auto:free` модель, що відмовила, паркується (7 діб, якщо «only available on agentic harnesses», інакше 6 год) і робота йде на наступній; 3 різні моделі з 403 в одному завданні = проблема ключа → черга зупиняється. З однією обраною моделлю 403 зупиняє, як і раніше.
- **Модель «лише для застосунків зі списку» зникає зі списку** (2026-10-26): після такого 403 `or_hide()` пише модель у `or_state.json` → `hidden` на `OR_HIDE_DAYS` (30) діб, `or_free_ranked()` її не показує й не пробує; потім вона повертається (раптом OpenRouter зніме обмеження). Виправити з нашого боку не можна: це заборона OpenRouter для застосунків не зі свого списку, а видавати себе за такий застосунок не можна. Так зникли `thinkingmachines/inkling` і `inkling-small`.
- Акаунти в «Адмін» показують двигун і статус оплати OpenRouter.

### Видалення з черги, перегляд файлів, світла тема (додано 2026-10-26)

- **«✕ Видалити»** біля кожного завантаження й запиту в черзі → `POST /api/queue/delete {id}` (`sb.delete_queue_item`). Що не обробляється, зникає одразу (`purge_item`: тека в `inbox/` або `requests/<id>.json`, `work/<id>`, мітка `run_now`, запис у `file_hashes.json`, щоб той самий файл можна було надіслати знову). Що обробляється зараз: у профіль іде мітка `cancel`, `Space.cancelled()` (дивиться на `cur_members`/`cur_item`/`current_rid` у статусі) зупиняє виклик моделі за секунди (Claude: цикл `communicate`; OpenRouter: між кроками; між порціями завантаження), `CancelledItem` (підклас `StoppedError`) доходить до воркера, а `purge_marked()` на початку кожного кола стирає елемент. Мітки, що лишились від мертвого воркера, чистяться при його старті. Видалити можна лише своє, лише `sub`/`req` (не пропозиції й не злиття). Прогрес обробки видаленого завантаження пропадає: якщо це учасник групи дрібних завантажень, решта групи починає спочатку (`pages.json` має інший склад).
- **Файли завантажень** (черга, «Не вдалося», «Нещодавно оброблено») мають посилання: `GET /api/upload/<id>/file/<n>` (`sb.upload_file`; лише власні, `n` = номер у `submission.json` → `files`, шлях не виходить за теку). PDF і фото показуються в браузері, текстові файли як `text/plain`, усе інше (Word, HTML, SVG, HEIC…) лише завантажується; тип береться з розширення зі списку `SHOWN`, не вгадується; для не-PDF `Content-Security-Policy: sandbox`.
- **Окремий файл із завантаження** (2026-10-26): у завантаженні з кількома файлами біля кожної назви в черзі є «✕» → `POST /api/queue/file/delete {id, file}` (`sb.delete_upload_file`; файл називається ЗБЕРЕЖЕНОЮ назвою з `file_links[].file`, не номером, бо список міг змінитися). Файл стирається, `files`/`original_names`/`label` оновлюються, запис про його хеш у `file_hashes.json` зникає (той самий PDF можна надіслати знову), уся напівготова робота цього завантаження й групи, до якої воно входило, скидається (сторінки решти файлів нумеруються заново). Останній файл = видалення всього завантаження. Те, що обробляється зараз, → 409 «видали повністю або дочекайся» (✕ тоді не показується).
- **Світла тема:** кнопка ☀/☾ біля перемикача мови; вибір у `localStorage.theme`, `data-theme="light"` на `<html>` ставить скрипт у `<head>` (без миготіння). Кольори в змінних (`--bg0`, `--pillbg`, `--dlg`, `--dot`, `--line2`, `--ph`, `--ul`, `--shade` додані до старих); зерно фону малюється для обох тем (база 236 проти 19) і перемальовується при перемиканні. Постер лишається «друкованим» в обох темах. Типово тема темна.
- Тест: `tests/test_queue_delete.py` (у т. ч. видалення завдання, на якому працює воркер).

### OpenRouter: коротша історія розмови (додано 2026-10-26)

OpenRouter не пам'ятає розмову: кожен крок агента надсилає всю історію заново. Один виклик `nemotron-3-ultra` за 80 кроків з'їв 3,75 млн токенів запиту (~47 тис. на крок), за день набралось ~14 млн. Більшість — текст, а не фото: прочитані файли (до 40 тис. символів кожен) і тексти, які модель записала через `write_file`. `or_compact()` перед кожним запитом: якщо минулі кроки (без системного повідомлення й завдання) важать більше за `OR_HISTORY_TOKENS` (16 000 оцінених токенів, `SB_OR_HISTORY`), їхній вміст стає короткими примітками `[omitted from the history: …]`, від найстаріших, до половини бюджету (тоді стиснений початок кілька кроків не змінюється). Що скорочується: вміст `write_file` (файл є на диску), вихід інструментів довший за 400 символів, фото, на які модель дивилась **до свого останнього запису**. Завдання й останні `OR_KEEP_TURNS` (2) кроки не скорочуються ніколи. У лозі `openrouter … ok` з'являється `shortened=N`. Тест: `test_openrouter.py` (модель `fake/bulky`).

### HTML-файли: конспект або інтерактивна сторінка (додано 2026-10-27)

Форма завантаження приймає `.html`, `.htm`, `.xhtml` (вид «Конспект»). Кожен файл сайт сам розпізнає (`classify_html` у `sb.py`):

- **Інтерактивна сторінка** (власний скрипт від 300 символів + керування: слайдер, кнопка, canvas, `addEventListener`…) **і** вона не порушує правил пісочниці `/i/` (ті самі `HTML_BAD`/`URL_RE`, що перевіряють пропозиції: без мережі, зовнішніх файлів, сховища, навігації; `<meta charset>` і viewport дозволені; до 1,5 МБ). Така сторінка зберігається **як є**, без моделі, у `interactive/<предмет>/` спільної книги (`add_interactive_html`): назва з `<title>`, тема `general` (або з форми), у метаданих `uploaded: true`, `sha` (та сама сторінка вдруге пропускається як дублікат). Потрібно обрати предмет, інакше 400. Відповідь API: `interactive: [{file, url}]`.
- **Звичайна збережена сторінка** (лекція, Moodle): `html_to_pages` → pandoc → markdown зі схемою `$…$` (формули MathJax `\(…\)` теж), скрипти/стилі/`<head>` відкидаються, картинки стають `(image: alt)` (збережені сторінки мають картинки окремими файлами, а base64 заливає модель), текст ріжеться на сторінки по ≈6000 символів між абзацами й іде далі як `.txt` (3 проходи). Кодування: UTF-8, інакше з `<meta charset>`, інакше cp1252.
- **Схожа на інтерактивну, але з мережею/зовнішніми файлами/сховищем:** читається як текст, а відповідь має `as_text: [{file, why}]` і сторінка пише причину.
- Завантажений HTML ніколи не віддається як сторінка сайту (`SHOWN` без `.html`: лише завантаження).
- Не підтримано: HTML як «PDF без редагування» (`asis`) і як підручник для звірки; картинки збереженої сторінки (окремі файли поруч) не підтягуються.
- Тест: `tests/test_html.py` (34 перевірки: текст, формули, розбиття, кодування, класифікація, весь шлях `api_upload`).

**Оновлення того ж дня (чинне):** інтерактивний HTML/JSX уже не зберігається «як є», а йде окремою заявкою `kind=ipage` (друга тека inbox) і проходить прохід ШІ: `add_ipages` у `sb.py`, промпт `prompts/ipage.md`, роль `ipage` (стеля sonnet, 40 ходів). Перевірки коду: `page_problems` = `looks_interactive` + `html_problems` (правила пісочниці) + `js_problems` (`node --check`); до `IPAGE_ROUNDS` (3) викликів. Предмет, який обрав студент, головніший; непридатну сторінку, що спершу була зламана, відхиляють; цілу, яку модель лише зіпсувала, кладуть як завантажено. Поле `code` у `/api/upload` приймає вставлений HTML або React-код (артефакти claude.ai не відкрити за посиланням: Cloudflare). Відповідь має `interactive: <кількість>`.

### Зміна інтерактивної сторінки на запит (додано 2026-10-27)

Праворуч від кожної сторінки в списку «Інтерактивні сторінки» є кнопка «Змінити»: відкриває поле для запиту й надсилає `POST /api/request` з `kind: "ipage_edit"`, `subject`, `stem`, `text`. Воркер (`process_ipage_edit` у `sb.py`, промпт `prompts/ipage_edit.md`, роль `ipage`) дає моделі копію `page.html`, тоді та сама перевірка `page_problems`, що й для завантаженої сторінки (до 3 кіл, не менше 40 % розміру, має відрізнятися від старої). Стара версія лежить у `<stamp>.prev.html`; кнопка «Скасувати зміну» (`POST /api/ipage/undo`) міняє їх місцями, повторне натискання повертає зміну. У метаданих: `edited`, `changes`, `edits` (останні 10: хто, коли, текст запиту), новий `sha`.
- **Хто може:** кнопка є в кожного, хто ввійшов. Власник книги змінює будь-яку сторінку, інші лише ті, що додали самі (`by` у метаданих; `can_edit_ipage`); зміна чужої сторінки лишає оригінал і додає окрему сторінку («… (changed)», `from`, `by`). Це вирішується ще раз у воркері. «Скасувати зміну» бачать лише ті, хто може змінювати сторінку. Один запит на сторінку одночасно (409). Сирий `by` назовні не йде: сторінка має `mine`, анонімам нічого з цього.
- **Назва на кнопці:** модель отримує правило «не більше 70 символів, що робить сторінка» (промпти `interactive.md`, `ipage.md`, `ipage_edit.md`), а код ще раз обрізає `page_title()` (`TITLE_MAX` = 70, по слову, з «…»). Опису теми поруч з кнопкою більше немає.
- Запит у списку «в процесі» має підпис «Зміна: …» (`making[].edit`); «Запустити зараз» працює й для нього.
- **Кнопка-посилання** на сторінку (`.gbtn`: форма — одна пілюля (від 34 px, кути 17 px) з кінцем «Змінити» справа, назва до двох рядків; форма — маска з градієнтів `--shape-*` на одній текстурі; верхній — посилання `a.glass`, нижній — «Змінити» `.gedit`, обидва на спільній текстурі без шва): заокруглена пілюля рубчастого скла збоку: тонкі горизонтальні ребра, зерно, світлий обідок, відблиск. Кожна кнопка різна: `ipVar(stem)` ставить `--p` (фаза ребер), `--r` (розмір ребер), `--b` (де найяскравіше), `--dir` (з якого боку). Посередині чорна підкладка тексту з розмитими краями (`mask-image` на `span::before`). Світла тема: ті самі змінні `--gl1/--gl2/--c0..c3/--band/--bt` з інвертованими кольорами (світле скло, темний текст). Без `filter`/`backdrop-filter`. Тонкий контур по краю (`.gring`, 1,5 px, без текстури скла) світиться там, де світла зона скла (`--b`, `--q`; вони тепер на `.gbtn` і успадковуються). Світла зона посередині, по боках темніше (`--b` = де найсвітліше, 40–60 % залежно від кнопки). Єдина анімація: поки курсор (або фокус клавіатури) на кнопці, світла зона текстури пливе до лівого краю, потім до правого й назад (цикл 3,6 с; слабша друга смуга йде в протилежний бік), ребра повзуть угору. Рух веде скрипт (`glassIn`/`glassOut`, Web Animations на `::before`), а не `:hover`: при відведенні курсора цикл не обривається, а доходить до кінця (де скло в спокої) удвічі швидше; швидке «навів-відвів-навів» продовжує той самий цикл без стрибків. `--b`, `--q`, `--p` оголошені через `@property`, базові значення лежать у `--b0`/`--p0`. Не діє, коли браузер просить менше руху.
- Тест: `tests/test_ipage_edit.py` (24 перевірки: хто може, 404 на шлях-хитрощі, черга, зміна, undo/redo, відмова при мережі й «без змін», повторна перевірка прав у воркері, стандарт письма в промптах).

## Підводні камені

- **pandoc не падає на TeX, який не може перекласти.** Він мовчки друкує його як буквальний текст `$$…$$`. Тому `check_md` ловить "Could not convert TeX math" у режимі `strict=True` і віддає файл Claude на виправлення (`prompts/fix.md`).
- **pandoc 3.7 і Typst 0.15 по-різному називають символи.** pandoc досі пише `sect` для `\cap`, `angle.l/r` для `\langle/\rangle`, `planck.reduce` для `\hbar`, `*.circle` для `\otimes` / `\odot` / `\circledast`. У Typst 0.15 цих імен уже немає, тож файл ішов у сирий фолбек, а fix-промпт не допомагав, бо LaTeX правильний. Тепер `fix_typst_symbols()` у `md_to_typst` перейменовує їх тільки всередині `$…$`. Список знайдено прогоном ~170 LaTeX-команд через pandoc → typst. Після оновлення pandoc/typst повтори цей прогін. Також змінилась сіль кешу (`typst-v2`).
- **Заголовкам `Cf-Access-*` і `Tailscale-User-*` через тунель не вірити.** Публічний екземпляр (`SB_PUBLIC=1`) ігнорує `Tailscale-*` повністю й сам перевіряє вхід (див. «Публічний доступ»); `Cf-Connecting-Ip` береться тільки для лімітів. Якщо колись з'явиться Cloudflare Access, треба перевіряти його JWT, а не заголовки.
- **Сторінка оновлює статус кожні 5 с** (`setInterval` → `/api/status`). Раніше кожне оновлення перебудовувало випадні списки й блок книг: відкритий список закривався, фокус злітав, «Теми» згортались. Тепер `setHTML` / `setOptions` / `setText` торкаються DOM, тільки коли вміст змінився. Поле вводу в фокусі не перебудовується (оновиться на наступному такті), а `<details data-k>` зберігають відкритий чи закритий стан. Перевірено в headless Chrome.
- `KillMode=process` у юніті: воркер, запущений із сайту, має переживати рестарт сторінки.

### Вигляд сайту (2026-10-26)

Темна тема (`color-scheme: dark`), шапка — постер за референсом людини: сірий папір, чорнильні квадрати, коротка назва (`app.short`: «КНИГИ» / «BOOKS») великими літерами, вирізаними з квадратів і обрізаними їхніми краями, поруч стовпчик дрібного тексту (повна назва + `app.tag`). Розкладку квадратів задає `CELLS` у `index.html`, будує `buildPoster()` (при кожній зміні мови).

Текстури процедурні й без тайлінгу: нічого не завантажується, JS малює їх один раз прямо в полотна (`paintTextures`, кожна у своєму `requestIdleCallback`; без кодування в PNG). Невидима маска лише задає силу зерна в кожній точці: для фону сторінки пом'якшений Voronoi (`voronoiField`, згладжений мінімум відстаней) у суміші з м'якими хмарами (`voronoiMix`, рахується в 1/4 роздільності), для паперу й чорнила хмари з довгими горизонтальними волокнами (`paperField`). Зерно симетричне навколо базового кольору й не обрізається, тож маску не видно (перевірено: середня яскравість блоків 18,5–19,5, сила шуму 1,7–6,9). Фон сторінки = полотно `#bg` на весь екран, `position: fixed` позаду всього (база 19, амплітуда 3–18; 4K отримує трохи крупніше зерно, ліміт 3,2 Мпікс). Папір постера = полотно-перший дочірній елемент `.poster` (перемальовується при зміні розміру > 15 %). Чорнило = одне полотно 720×720 CSS px у пам'яті, кожен квадрат має своє полотно й копіює з нього свою ділянку (`drawCells`, `--bp`). Заміри в headless Chrome на ноутбуці: фон Full HD ~85–120 мс, чорнило ~40 мс, папір ~20 мс. WebGL-варіант пробували 2026-10-26: тут він повільніший (контекст + компіляція шейдера ~260 мс), тому його немає.
